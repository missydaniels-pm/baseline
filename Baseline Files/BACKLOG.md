## Decision Log

### FK cleanup — Increment 2: the database owns cascading (completes the milestone)
**August 8, 2026:** Removed the hand-ordered child cleanup; `passive_deletes=True` on 11 relationships means SQLAlchemy no longer loads and deletes children in Python. `delete_account` went from ~14 bulk deletes to `db.session.delete(user)`; `delete_protocol` from 4 statements to 1; `delete_episode` no longer manually detaches check-ins; `dev_reset` from 11 statements to 6. Net **app.py −55/+30**, concentrated in the delete paths where the ordering was the fragile part.

**Deployed only after** `check_fk_orphans.py` and `verify_fk_ondelete()` both came back clean on staging *and* production — the Increment 1 prerequisites, which mattered because the constraints are now load-bearing rather than decorative.

**The assertion worth keeping:** `test_fk_ondelete.py` counts SQL statements and requires a fully-populated user delete to emit **exactly one DELETE**, against `users`. If `passive_deletes` is ever dropped or a future edit reintroduces eager loading, the ORM quietly starts doing the work again and everything still *passes* functionally — this is the only thing that would catch it.

**Deliberately not cleaned up:** `cleanup_stale_unverified_users()` still anonymizes `UserActivity` by hand. It needs the opposite of the declared CASCADE (a never-verified signup should still count in analytics), and "finishing the cleanup" there would have silently started deleting signup data.

**Reviewed** QA + Code — **1 blocker, fixed.** `delete_account` was left with no `except IntegrityError` while its two siblings got one, and `resend_contact_delete()` fired *before* the DB write — so on an environment with bad constraints the user would be dropped from the mailing list while their account and health data survived, behind a raw 500 in the middle of "delete my health data." Now guarded, with the Resend call moved after a successful commit. Also fixed: a stale `database.py` comment claiming `delete_account` still bulk-deletes triggers, a missing 2-hop assertion in the new ORM test (QA), and the **CONVENTIONS "Deletes" section, which post-Increment-2 would have actively instructed the next contributor to re-add hand-ordered cleanup to `delete_account`** — rewritten to describe the new pattern and `dev_reset`'s documented exception.

**Owner decision (A1) — gate the delete routes.** `check_fk_ondelete()` stays warn-only for the app as a whole, but its result is recorded in `FK_SCHEMA_PROBLEMS` and every hard-delete route now begins with `deletion_blocked_response(...)`: on a mismatch it refuses and flashes instead of deleting, and logs at ERROR. Rejected making startup fatal — one wrong FK shouldn't take the app down for every user. This targets the *silent* failure (a `SET NULL` column actually set to `CASCADE` destroys an experiment or chat history with no error); the loud failure (`CASCADE` actually `NO ACTION`) was already caught by the `IntegrityError` guards. Verified by simulating a mismatch: both episode and account deletion refused, data intact, error logged; restored, deletes work. Rule 1 is satisfied — `FK_SCHEMA_PROBLEMS` is derived at boot from the shared DB, so every instance computes the same value (same category as `CSS_VERSION`), not per-server state.

### FK cleanup — Increment 1: DB-level ON DELETE directives
**August 8, 2026:** All 20 FKs now carry `ON DELETE` (16 CASCADE, 3 SET NULL, declared once in `database.EXPECTED_FK_ONDELETE`). **Behaviour-preserving by design:** the hand-ordered child cleanup still runs first, so the constraints are inert safety nets until Increment 2. Both reviewers independently traced every delete route and confirmed nothing user-facing changes.

**Owner decisions:** (a) **no SQLite rebuild migration** — SQLite can't alter constraints in place and is dev-only; a fresh local DB gets correct constraints from `create_all()`. Missy pushed back on whether that risks local/prod drift, which was the right question: it does, but the SQLite-rebuild alternative wouldn't have caught it either (a SQLite rebuild ≠ the Postgres ALTER, so exercising one proves nothing about the other). The actual mitigation is the **schema assertion**, added because of that challenge — `verify_fk_ondelete()` holds both engines to the same declared matrix, and `check_fk_ondelete()` warns loudly at startup. (b) **Two increments** — separates "did the migration apply" from "does the app behave right when the DB cascades." (c) `user_activity.user_id` CASCADE (matches current behaviour + privacy-first).

**Beyond the plan:** the PostgreSQL branch never executes locally, so it would have first run on staging unproven — extracted to `migrate_fk_ondelete()` and driven with a fake conn/inspector (20 DROP+ADD pairs, correct directive each, idempotent no-op when re-run). Added `check_fk_orphans.py`, a read-only pre-flight for the one risk nothing local could settle: `ADD CONSTRAINT` validates existing rows, so a single orphan would leave that FK on `NO ACTION` while the rest migrated. Verified it detects a planted orphan.

**Found during the work, both worth remembering:** (1) `test_triggers.py` asserted that deleting an episode with live trigger links *raises* — it documented the old contract, and its failure is the clearest evidence the DB-level contract genuinely changed even though app behaviour didn't. Updated to assert the new one. (2) `cleanup_stale_unverified_users()` **anonymizes** UserActivity while `delete_account` **deletes** it — one FK, two desired behaviours. Neither reviewer caught it. The explicit UPDATE is now marked load-bearing for Increment 2; removing it would silently start deleting signup analytics.

**Reviewed** QA + Code — **0 blockers**. Fixed: an unguarded `verify_fk_ondelete()` call that could crash startup and contradict its own warn-only docstring (both reviewers), a duplicated line I left in the test edit (both reviewers), and a stale comment claiming SQLite doesn't enforce FKs. Code's A1 was right that "single source of truth" was aspirational — the dict only checked itself against the live DB and was blind to a model FK never added to it; `test_fk_ondelete.py` now walks `db.metadata` in both directions, verified by deleting an entry and watching it fail.

### Bug: duplicate records from double-tapping Save — client submit guard
**August 8, 2026:** Owner-reported ("the confirmation message is slow, so I hit Save more than once"). **Reproduced before fixing:** two concurrent POSTs to `/episodes/new` created two identical episodes. Swept every POST route — the exposure was `/episodes/new`, `/protocols/new`, `/rescue-options/new`, `/experiments/new` (none has a duplicate-name guard); `/symptoms/new`, `/register`, custom triggers, and compliance logging were already protected by uniqueness checks or upsert, and `/checkin` had its own client guard.

**Owner decision:** ship the **client guard now**, spec DB-backed idempotency keys for the rebuild. A correction was needed first — the earlier framing implied server-side idempotency would violate Rule 1. It does not: Rule 1 governs *where* state lives, and a keys table in the shared DB is compliant. `UsedVerifyToken` (`database.py:352`) is already structurally that. So waiting for React buys nothing on the constraint; it buys ergonomics (a real API client minting `Idempotency-Key` headers) and shared machinery with the async check-in job.

**Shipped:** one global guard in `base.html` — a `submit` listener on `document` in the **bubble** phase (required, so `e.defaultPrevented` correctly reports a cancelled `confirm()` or failed validation and the form is never latched shut on a submit that isn't happening). `data-submitting` on the form is the real protection; `data-guard-disabled` on its buttons is feedback only. A `pageshow` handler releases the latch on bfcache restore. Every validator that recomputes a button's `disabled` on input now respects the latch (char-limit guard, `settings.html` ×2, `register.html`). In-flight feedback is a CSS-appended ellipsis (`.btn[data-guard-disabled]::after`) rather than per-button busy labels — one rule for every verb in the app, no stale-text risk; costs ~15px of layout shift.

**Review found 2 blockers, both fixed.** (B1) **`form.submit()` dispatches no `submit` event**, so six call sites silently bypassed the guard — including the "active experiment → continue anyway" modal on `/protocols/new`, `/protocols/<id>/edit`, `/experiments/new`, i.e. three of the four routes named as exposed. QA independently reproduced two duplicate `Protocol` rows through it. Fixed with `.requestSubmit()`, which also restores the constraint validation `.submit()` skips — that in turn exposed a **separate pre-existing bug: blank names create nameless records** on three create routes (logged under Open Bugs). (B2) The guard's `pageshow` release re-enabled check-in's Send button without clearing check-in's *own* `submitting` flag or "Sending…" label — a button that looked live but silently swallowed every tap, exactly the pattern CONVENTIONS.md forbids. Fixed with a check-in-side reset that also drops the optimistic bubble and typing indicator for a send that never landed.

**Explicitly NOT covered, and not to be described as fixed:** two browser tabs (QA verified two tabs still produce two episodes — the flag lives in one tab's DOM) and any retried/replayed request. Those need the idempotency keys.

**Rejected — a safety-timeout that auto-releases a latched form.** Both reviewers suggested one (~15–20s) for a request that never resolves. Investigated and dropped, not deferred. (a) Closing/reopening the app already clears it — the latch is in-memory DOM state, never rendered into the HTML; verified by reloading a latched form. A backgrounded-and-resumed PWA is covered by the `pageshow` release. (b) The only real cost of *not* having it is retyping unsaved input after a full relaunch. (c) That cost is a classic-form-POST artifact: the browser owns the navigation and JS gets no completion signal, so a timer is a guess standing in for the callback you can't have. The rebuild's `fetch`-based submits always resolve/reject/abort (re-enable in `finally`, bound with `AbortController`) and React holds form state in memory, so both the timer *and* the retyping problem disappear by construction. **Do not schedule this for the rebuild — it is not needed there either.** The retry-duplicate risk it gets confused with is architecture-independent and belongs to the idempotency-key row. Owner decision 8/8/26.

### User Timezone — Increment 3: check-in time-resolver (completes the milestone)
**July 17, 2026:** Replaced the AI check-in's freehand-onset anti-pattern (the model computing an ISO datetime — the "model does date math" class that produced the 7/14 bug elsewhere) with **classify-and-resolve** (spec §1.2/§2). The prompt now returns `onset_time_expr` (verbatim phrase) + `onset_time_type` (enum); deterministic `resolve_onset()` resolves it against the message anchor (`_client_time_anchor()` → `user_now()`) via `dateparser` + a small colloquial-normalization layer, and never logs a future onset (clamps). Low-confidence resolutions ride a light "adjust the time" nudge through the existing episode edit form (no new UI). New dep `dateparser>=1.2`; `test_onset_resolver.py`. Verified against the live model (returns the new fields; "last night around 10" → Thu 22:00). **Owner decision:** keep the small hand-rolled normalization (Code A1 Option A) rather than `dateparser.search_dates` — smaller/faster/tested; revisit if real check-ins keep producing unhandled phrasings.

### Timezone Bug — `baseline_tz` Cookie Encode/Decode + `user_today()` Single Source of Truth

### Today's Protocols — Tri-State Partial Logging & Un-Log (revisiting "Assumed Taken")
**July 14, 2026:** Missy reported that logging one preventative protocol and leaving the others blank marked *all* of them taken on Confirm, with no way back to unmarked — she takes protocols morning and night and wanted to log just what she'd completed. Root cause was the intended "assumed compliance" behavior (`took: state.took !== false` wrote every blank as taken) combined with flip-only pills (no clear) and no delete path. Because the fix overrides the documented "assumed compliance" philosophy, it was raised to Missy before building; she specified the design. Decisions:
1. **State-driven button, not a philosophy change.** "Assumed compliance" is preserved as the *default fast path*: when nothing is explicitly marked the button reads **"Confirm all as complete"** (one tap writes all taken, unchanged). The moment anything is marked or cleared it becomes **"Save"**, which writes exactly what's set and leaves blanks unlogged. This keeps the one-tap happy path while making partial logging honest — the app no longer invents "taken" for protocols the user didn't touch once they've started marking.
2. **Tri-state pills with tap-again-to-clear** on the today card (matching the backfill editor), replacing flip-only. The old dashed "assumed-taken" pre-selection styling was removed so a blank pill reads as genuinely neutral; the assumption now lives only in the button label. `.tp-pill-assumed` CSS deleted.
3. **Un-log = delete the row.** `POST /protocols/log-day` `took` became tri-state (`true`/`false`/`null`); `null` routes through a new `_delete_compliance()` in `_commit_compliance()`, so a protocol can return to unmarked even after it was confirmed. Deletes are idempotent → safe on the existing IntegrityError retry. Backfill Save also sends tri-state so clearing a past entry removes it. Validation rejects non-bool/non-null `took` with 400 before any write (no partial writes); the shared `_upsert_compliance()` and its other callers (protocol-detail form, AI check-in) still pass only bools and are unaffected.
4. **Relabel Taken/Missed → "Complete"/"Not Today"** (owner's call) to remove medication bias — protocols include lifestyle/dietary/routine changes, not just meds. Applied to today rows, backfill editor, bulk button ("Mark all Not Today"), done-state summary, dot aria-labels, and help copy.
5. **Partial save is a first-class state:** leaving some protocols blank keeps the card expanded with a "Partly logged" chip and "Saved. The rest are still open for today." — supports the morning-then-night logging rhythm.
6. **Accepted edge (flagged at deploy):** clearing *every* protocol flips the button back to "Confirm all as complete", so the primary button can't clear a whole day to hollow in one press (all-blank is defined as the confirm-all shortcut, per spec). Un-logging works whenever at least one protocol stays marked. A dedicated "clear today's log" affordance is a possible future add if this friction shows up in use.
Verified with a Flask test-client suite (confirm-all, partial, un-log, invalid-type 400/no-partial-write, note validation + preservation, day_status recompute) and a real-browser Playwright pass at 375px driving the card end-to-end (bug reproduction confirmed fixed, tap-to-clear, un-log-one-keep-another, note-clears-on-clear, no label overflow).

**Review-driven hardening (same session, QA + Code + UX agents):** (a) clearing a "Not Today" pill now also clears its note field so a typed note can't silently ride onto a Complete/blank state or be discarded on confirm-all; (b) the backfill editor carries each protocol's existing note through unchanged on Save (`bfNote`) — previously it resent `note:''` for every protocol, which could blank out a note set via the detail form or AI check-in; (c) non-string `note` in the JSON body now returns 400 instead of a 500; (d) `protocol_detail.html` relabeled Taken/Missed → Complete/Not Today (log form + history timeline) so both compliance entry points share one vocabulary; (e) per-protocol `aria-label`s on the pills (today + backfill); (f) focus moves to the "change something" link after a full save collapses the card; (g) a saved-but-incomplete day shows a "Partly logged" chip on reload, not the generic default.

**Deploy-Gate decisions (resolved by Missy 7/14/26):**
1. **Partial-day dot color → Option A (chosen).** All three reviewers flagged that a partially-logged today (e.g. 1 of 3 Complete, rest left blank) rendered a **green** dot labeled "all complete" while the card said "Partly logged" — because the old 7/12 rule "partial-but-all-taken counts as green (positive framing)" now fired routinely on today. Fixed: green is awarded only when *every* active protocol for the day is logged and Complete; a partial-no-miss day is now **amber**. Implemented via a single `_compute_day_status()` helper shared by the server render and the AJAX recompute (also closes the render/AJAX divergence Code Review raised). Overrides the 7/12 positive-framing decision, with the owner's approval. Dot aria-labels + help copy updated.
2. **Concurrent clear-vs-write lost update → accepted + documented.** `_delete_compliance` racing a concurrent stale `took=true` write isn't caught by the IntegrityError retry (delete raises no IntegrityError). Low frequency at 5 users; revisit with row-versioning/optimistic-locking at scale.
3. **Dedup migration tie-break (pre-existing) → flagged, not changed.** The 7/12 `run_migrations()` dedup keeps `MIN(id)` (oldest) rather than `MAX(id)` (newest), contradicting "most recent wins." It already ran in production behind `IF NOT EXISTS`, so re-running won't re-dedup — left as-is; do a one-time prod check (`GROUP BY user_id,protocol_id,date HAVING COUNT(*)>1`) and use `MAX(id)`/`MAX(created_at)` if a similar migration is ever written again.

### Binary Tracked-Item Storage — Separate Column vs Reused `score`
**June 2026:** For the Yes/No tracked-item type (Spec 01), chose to add a new nullable `value_bool` column on `SymptomScore` rather than overloading the existing `score` column with 0/1. Trade-off considered: reusing `score` would have saved a column add but creates a real footgun — any aggregate that sums or averages `score` without joining `Symptom` to check `input_type` would treat a binary `1` as a scale `1`, silently corrupting trend lines and correlations. With separate columns, every existing scale aggregate keeps working unchanged because `score IS NOT NULL` naturally excludes binary rows, and the same shape extends cleanly to the future categorical/count types the spec calls out. Cost: one nullable column on the entries table and slightly more code on the write path. Worth it. Decision is per-spec, not per-symptom — `Symptom.input_type` remains the single source of truth for which column to read.
